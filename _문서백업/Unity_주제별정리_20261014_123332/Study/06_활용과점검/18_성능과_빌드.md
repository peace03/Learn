# 18. 성능과 빌드

> 모르는 단어는 [전문 용어 전체 색인](../90_%EC%B0%B8%EA%B3%A0/%EC%9A%A9%EC%96%B4_%EC%82%AC%EC%A0%84.md)에서 영문·한글로 찾습니다. 이 장 맨 아래에는 등장 용어의 바로가기 목록이 있습니다.

## 빠르다는 말을 시간으로 바꾸기

준비 B의 프레임·FPS, 준비 C의 픽셀 수·렌더링이 선수 개념입니다. **성능**은 주어진 일을 얼마나 빨리, 얼마나 적은 자원으로 처리하는가입니다. **메모리**는 사용 중인 값을 담는 공간이고, **병목**은 전체 진행을 늦추는 가장 큰 제한입니다. 삼각형 수·텍스처 크기 중 하나만 줄였다고 병목도 반드시 줄지는 않습니다.

`ms`는 밀리초로 1초의 1/1000입니다. 60FPS의 약 16.7ms는 CPU와 GPU의 모든 시간을 단순 합한 값이 아닙니다. 둘이 앞뒤 프레임 작업을 겹쳐 할 수 있고 기다리는 시간도 있습니다. **VSync**는 화면 표시 주기에 맞춰 프레임 출력을 조절하므로 계산량이 줄어도 FPS 숫자가 그대로일 수 있습니다.

**빌드**는 편집기 밖에서 실행할 프로그램을 만드는 일, **Player**는 그 실행 환경입니다. **플랫폼**은 Windows처럼 실행할 환경, **Development Build**는 측정·진단을 돕는 개발용 빌드입니다. Editor에서만 쓰는 코드는 Player에 없는 기능을 참조할 수 있으므로 분리해야 합니다.

Profiler에서 기록 버튼을 켜고 같은 동작을 관찰한 뒤 기록을 멈추면 프레임 하나를 클릭해 읽을 수 있습니다. CPU Usage는 처리 시간, Rendering은 그리기 통계, Memory는 메모리 사용을 보는 모듈입니다. 수치가 제공되지 않는 GPU 항목을 0ms라고 적지 않습니다. 지원 여부와 측정 대상을 기록합니다.

## 속도를 숫자로 읽는다

FPS는 초당 화면 수, 프레임 시간은 화면 하나를 만드는 데 든 시간입니다.

```text
프레임 시간(ms) ≈ 1000 / FPS
60 FPS → 약 16.7ms
30 FPS → 약 33.3ms
```

CPU는 게임 규칙·그리기 준비를, GPU는 정점·픽셀 등 그래픽 계산을 주로 처리합니다. 실제 실행은 겹쳐 진행되므로 두 시간을 무조건 더해 FPS를 계산하지 않습니다. 어느 쪽이 기다리는지 보는 것이 중요합니다.

## 자주 보는 성능 용어

| 용어 | 뜻 | 이 프로젝트에서 볼 곳 |
|---|---|---|
| Draw Call / Batch | 그리기 명령·묶음 | 여러 메시와 재질 |
| SetPass | 그리기 상태·셰이더 패스 전환 | 다양한 재질·렌더 패스 |
| Overdraw | 같은 픽셀을 겹쳐 그림 | 먼지·투명 표면·UI |
| Fill Rate | 픽셀 처리 능력 | 고해상도 반사·후처리 |
| GC Alloc | 관리 메모리의 새 할당 | 매 프레임 문자열·컬렉션 생성 여부 |
| LOD | 거리에 따라 단순한 모델 사용 | 원거리 표시 비용 |
| Mipmap | 작은 크기로 미리 만든 텍스처 단계 | 먼 거리 표면 품질·대역폭 |
| SRP Batcher | 호환 재질의 CPU 설정 비용 완화 | URP 재질 처리 |

SRP Batcher를 켰다고 모든 물체가 하나의 Draw Call이 되는 것은 아닙니다. 삼각형 수 하나만 낮다고 빠른 장면도 아닙니다.

## 현재 비용 후보

- Main Camera의 평면 반사 해상도는 Full. 추가 카메라 렌더를 요청합니다.
- PC 그림자 텍스처 설정은 Main·Additional 모두 8192. 실제 메모리·비용은 포맷·광원 수·아틀라스 사용 등에 따라 달라집니다.
- 스튜디오에 여러 Spot Light가 있습니다.
- PC Renderer에는 SSAO·Screen Space Shadows·Decal 기능이 있습니다.
- 먼지와 투명 재질은 화면에서 겹치는 정도에 따라 픽셀 비용이 늘 수 있습니다.

이는 **측정할 후보**입니다. 실제 병목이라고 확인된 목록이 아닙니다.

## 실습: Profiler 비교

1. 같은 씬·카메라·Game 해상도·품질을 정합니다.
2. `Window > Analysis > Profiler`를 엽니다.
3. Play를 켜고 임포트·초기 준비가 지나간 뒤 CPU Usage·Rendering·Memory를 확인합니다. GPU 모듈 지원은 환경에 따라 다릅니다.
4. 반사 Full → Half만 바꾸고 비슷한 구간의 프레임 시간을 비교합니다.
5. 다시 원래 조건으로 돌리고 먼지나 추가 효과를 하나씩 비교합니다.
6. `Window > Analysis > Frame Debugger`로 한 프레임의 그리기 단계를 확인할 수 있습니다. 사용 후 Enable을 꺼 둡니다.

Profiler의 Editor 측정에는 편집기 자체 비용도 섞입니다. 배포 성능 판단은 나중에 대상 기기의 Development Build에서도 확인합니다. VSync·프레임 제한에 막혀 FPS가 같아도 GPU 작업량은 달라질 수 있습니다. [Profiler 문서](https://docs.unity3d.com/6000.0/Documentation/Manual/Profiler.html).

## 빌드: 편집기 밖에서 실행할 프로그램 만들기

프로젝트를 Play하는 것과 실행 파일을 만드는 것은 다릅니다. 현재 자료는 **빌드 통과를 확인한 상태가 아닙니다.** 특히 다음 두 사실부터 알아야 합니다.

1. 저장된 기본 Build Scene 목록에는 `SampleScene`만 켜져 있습니다.
2. `05.Editor` 아래와 `Lab_Varco3D` 아래에 `UnityEditor`를 직접 사용하는 코드가 있고, 대부분 정확한 `Editor` 폴더·Editor 전용 asmdef·`UNITY_EDITOR` 조건으로 분리되지 않았습니다.

`05.Editor`라는 이름만으로 Editor 전용 컴파일이 되지 않습니다. Unity의 특수 폴더는 정확히 `Editor`입니다. [특수 폴더 규칙](https://docs.unity3d.com/6000.0/Documentation/Manual/SpecialFolders.html).

## 먼저 해결해야 할 코드 경계

배포 작업을 따로 할 때 선택 가능한 원칙은 다음과 같습니다.

- 순수 Editor 파일은 정확한 `Editor` 폴더 또는 Editor만 포함하는 asmdef로 분리.
- 공용 파일 안의 일부 Editor 코드만 제외해야 하면 적절한 `#if UNITY_EDITOR` 경계 사용.
- Editor 타입을 런타임 코드가 참조하지 않도록 의존 방향 확인.

패키지 Bridge는 이미 `VARCO3DBridge.Editor.asmdef`의 includePlatforms가 Editor입니다. Assets의 도구 코드와 같은 상태로 묶어서 설명하면 안 됩니다. 폴더 이동은 `.meta`와 참조를 유지하도록 Unity Project 창에서 수행하고, 이동 후 Editor 컴파일과 Player 빌드를 따로 확인합니다. 이 문서 작업에서는 이러한 이동·수정을 수행하지 않았습니다.

## 빌드 준비가 된 뒤의 클릭 순서

1. 실습 씬을 저장하고 `File > Build Profiles`를 엽니다.
2. Windows 등 목표 플랫폼 프로필을 고릅니다. 필요한 Build Support가 없다면 Unity Hub의 해당 Editor 설치에서 모듈을 추가해야 합니다.
3. 실제 사용할 프로필의 **Scene List**를 엽니다. 공유 목록을 쓰는지 프로필별 Override를 쓰는지도 확인합니다.
4. `Add Open Scenes` 또는 Project의 씬 파일 드래그로 실행할 실습 씬을 넣습니다.
5. 켜진 씬 중 처음 실행할 씬을 맨 위로 옮깁니다. 기본 SampleScene만 남아 있지 않은지 확인합니다.
6. 처음 검증은 `Development Build`를 사용하고, 필요하면 `Autoconnect Profiler`를 선택합니다.
7. `Build` 또는 `Build And Run`을 누르고 `Builds/Windows` 같은 **Assets 밖의 출력 폴더**를 선택합니다.
8. Console의 첫 빌드 오류를 확인합니다. 성공 후 실행 파일에서 카메라·UI·애니메이션·재질을 다시 확인합니다.

Build Profiles의 메뉴 목적은 [Unity 공식 설명](https://docs.unity3d.com/6000.0/Documentation/Manual/build-profiles.html)을 참고합니다. 활성 플랫폼·실제 Build Profile은 이번 작업에서 Editor로 조회하지 않았습니다.

## 저장·이동·공유

다른 PC로 프로젝트를 옮길 때 기본 원본 묶음은 `Assets + Packages + ProjectSettings`입니다. 에셋의 `.meta`를 함께 보존합니다. `Library`는 일반적으로 재생성할 수 있는 캐시이지만, 패키지 다운로드·임포트에 다시 시간이 필요합니다.

현재 Bridge manifest에 외부 절대경로가 남아 있으므로 다른 PC에서는 embedded 패키지 인식 상태까지 확인합니다. `Packages/packages-lock.json`을 보고 모든 환경이 자동으로 재현된다고 단정하지 않습니다.

실행 파일만 전달할 때도 `.exe` 하나만 떼지 말고 Unity가 만든 해당 빌드 출력의 필요한 파일·폴더를 함께 전달합니다.

## 단계별 확인표

| 단계 | 통과 의미 | 대신 증명하지 못하는 것 |
|---|---|---|
| C# 컴파일 | 소스가 현재 대상에서 컴파일됨 | 임포트·재생·외관 |
| 에셋 임포트 | Unity가 데이터를 읽음 | 원하는 재질·움직임 |
| Preview | 선택한 에셋의 미리보기 | 실제 씬의 연결과 입력 |
| 씬 Play | Editor에서 해당 흐름 실행 | Player 빌드 성공 |
| Player 빌드 | 대상 실행 파일 생성 | 해당 PC에서의 정상 동작·성능 |
| 실행 파일 검증 | 시험한 조건에서 실행 확인 | 모든 플랫폼·모든 입력 |

**확인 질문:** Editor에서 잘 실행되는데 빌드가 실패할 수 있는가? Render Scale을 0.8로 줄이면 전체 실행 시간이 항상 64%가 되는가?

**답:** Editor 전용 코드·플랫폼 차이로 실패할 수 있습니다. 줄어드는 픽셀 수와 전체 작업 시간은 다릅니다.
